# Vaporize v0.0.1 - wrkstrm App Minimums

**Status:** release-prep requirement; implementation follow-up
**Component:** `vaporize@wrkstrm-core.cli`
**Reference specimen:** `hello-world-google.demo`

## Purpose

Vaporize must know whether a wrkstrm app satisfies the minimum app build and
release-feature topology before it presents build, size, cache, or launch
evidence as trustworthy.

This is not optional decoration. If Vaporize cannot tell whether these surfaces
exist, then it cannot honestly say which feature cohort, release tier, or app
configuration it built.

## Minimum Surfaces

For each wrkstrm-owned Apple app, Vaporize app inspection should report:

| Minimum | Required evidence |
| --- | --- |
| App registry record | wrkstrm-core `xcode-project.tool.json` record or equivalent `tool-registry@wrkstrm-core.cli discover-apps` result |
| Project spec | `project.yml` or forward Pkl project spec path |
| Build configurations | `Debug`, `Dogfood`, `TestFlight`, and `Release`, unless the app declares an approved alternate tier set |
| Release feature manifest | `Config/release-features.json` with tier entries containing `id`, `xcodeConfig`, `displayName`, `compilationCondition`, and `features` |
| Generated xcconfigs | One `Config/xcconfigs/<XcodeConfig>.xcconfig` per tier, generated by `digikoma-release-features`, containing `SWIFT_ACTIVE_COMPILATION_CONDITIONS` |
| Project wiring | `project.yml` `configFiles` or Pkl equivalent maps each Xcode configuration to the generated xcconfig |
| Generated Swift facade | `Sources/ReleaseFeatures.swift` generated by `digikoma-release-features` |
| Generator provenance | Receipt or in-file generated headers showing `digikoma-release-features` produced the xcconfigs and Swift facade |
| Launch gate integration | Future launch-review status should include `releaseFeaturesEmitted`; localization audit status should include `localizationAuditPassed` when the app carries the audit phase |

## Status Vocabulary

Vaporize should report each minimum with a status:

- `pass`: required surface exists and is wired to the app.
- `missing`: required surface is absent.
- `stale`: generated surface exists but does not match the manifest or receipt.
- `unknown`: Vaporize cannot prove freshness yet.
- `not-applicable`: the app has an explicit approved alternate topology.

Missing or stale minimums must block strong app-facing claims about feature
cohorts, per-feature build size, launch readiness, or release-tier behavior.

## Hello World Google Specimen

`hello-world-google.demo` is the reference specimen.

- `project.yml` declares the tiered configs:
  `Debug`, `Dogfood`, `TestFlight`, and `Release`.
- `project.yml` wires those configs to generated files under
  `app/hello-world-google.demo/Config/xcconfigs/`.
- `Config/release-features.json` is the source of truth for tiers, compilation
  conditions, and feature lists.
- `Config/xcconfigs/{Debug,Dogfood,TestFlight,Release}.xcconfig` are generated
  by `digikoma-release-features`.
- `Sources/ReleaseFeatures.swift` is generated by `digikoma-release-features`.

## Vaporize Follow-Up

Required product follow-up:

`FR-VAPORIZE-WRKSTRM-APP-MINIMUMS-INSPECTION`

Acceptance:

- Vaporize accepts an app record or app path and reports the minimum surfaces
  above.
- Vaporize can scan the wrkstrm app fleet and emit a machine-readable receipt.
- Vaporize runtime samples for app builds include the minimum-status summary
  and the release-feature tier/cohort used for the build.
- Vaporize refuses strong feature-cohort, launch-readiness, or per-feature-size
  claims when minimum status is `missing`, `stale`, or `unknown`.
